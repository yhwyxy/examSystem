# 可信评分灰度发布与回滚手册

本手册定义 P7 的分阶段上线顺序。它是操作流程，不表示已连接或修改生产环境。首次执行必须在隔离演练环境完成；每阶段的执行人、时间、候选镜像摘要和证据应写入发布记录。

当前代码已有具名账号与 `editor`、`reviewer`、`publisher`、`admin` 角色。发布 API 已强制要求当前轮次的评分、P3 相似性报告和 P4 异常报告齐备，并拒绝未解决的阻断级 P4 线索；这些服务端门槛在 rollout 中持续开启。P3/P4 报告只提供核查线索，不改写分数。试点的“只观察”阶段通过不向试点人员开放发布账号、也不执行发布操作来实现。管理员本身具备发布能力，因此其凭据必须由独立发布负责人保管。

## 0. 发布前准入

只有下列证据齐备后才能进入试点：

- 候选 Go 服务、worker 和 `subjective-scoring` 发布版本固定且记录了源码提交与镜像摘要；当前依赖的库版本是 v0.1.13。若升级评分库，先完成库发布、离线包更新和 examSystem 依赖锁更新，并通过隔离 sandbox 的执行验证。
- P6 使用获批的去标识样本、真实候选模型预测、两位独立标注员和逐例仲裁结果；保存模型/provider 版本、评分配置指纹、标注协议和评估报告。阈值由团队先审阅基线再书面批准，不能从合成测试或旧的单份参考分推定。
- 代码检查、Go 与 Python 回归、worker preflight、镜像构建和迁移 rehearsal 通过。记录未解决问题及明确的继续/停止决定。
- 发布负责人、复核负责人和回滚负责人已具名；生产 `.env` 凭据单独保管，试点复核人员没有 admin 或 publisher 凭据。

尚未取得以上证据时，保持“只观察、不开发布”的状态，不扩大样本或发布成绩。

## 1. 备份与迁移演练

在与生产隔离的主机、独立 Compose project 和独立 `data/` 目录中演练。不要让恢复步骤指向生产卷或工作目录。先用部署仓库脚本生成完整备份并校验清单：

```bash
./scripts/backup-prod.sh
cd backups/<时间戳-唯一后缀>
sha256sum -c SHA256SUMS
```

先确认 `BACKUP_COMPLETE` 和三项校验清单完整，按 [恢复手册](deployment-restore.md) 在新目录、新 Compose project 与空数据库卷中成组还原。以下命令仅在该隔离恢复目录执行；`COMPOSE_PROJECT_NAME` 必须设置为该次恢复项目名。校验历史轮次与文件快照一致后，使用候选镜像应用增量迁移并启动服务：

```bash
docker compose -f docker-compose.prod.yml up -d postgres
docker compose -f docker-compose.prod.yml run --rm exam migrate --config /app/config.yaml
docker compose -f docker-compose.prod.yml up -d --no-deps exam
docker compose -f docker-compose.prod.yml ps
curl --fail http://127.0.0.1:8000/api/health
docker compose -f docker-compose.prod.yml run --rm --no-deps worker \
  python -m scoring_worker --preflight
```

保存迁移输出、健康响应、容器状态、preflight 输出，以及抽查历史轮次的结果。迁移记录校验文件校验和；已发布的 migration 文件不可编辑，也没有自动 down migration。若演练失败，丢弃隔离副本并从该次备份重建后重试，不能把此步骤改为对生产数据试跑。

核准恢复后的队列、凭据与评分配置后才启动 worker。仓库也提供 `python scripts/rehearse_restore.py --baseline-ref 8783a88a3add974f554dd79a62f887ad533d45e2 --output-root /private/tmp/exam-restore-rehearsals`，需按恢复手册设置独立本地管理员数据库环境变量。2026-10-13 原生 PostgreSQL 合成演练已通过 schema 2 → 11、真实 dump/psql 恢复、历史分数与审计保留、文件快照校验、基线旧程序读取恢复旧 schema 及再次升级。报告记录基线提交和两个程序的 SHA-256；它没有证明 Docker 部署或已批准生产版本的回退兼容性。

## 2. 小范围试点

选定有限的试卷、轮次和复核人员；记录候选版本与范围。先完成一次端到端收卷和评分，检查提交状态、评分代次、人工复核入口和历史版本。暂不创建或分配 `publisher` 账号，不执行发布请求。试点样本需覆盖实际启用的题型、语言、评分模式和已知降级路径。

任何必要复核未完成、报告过期、P4 阻断线索未解决或评分超出有效范围时，都应保持轮次未发布，按现有工作队列处理；不得用直接数据库写入绕过门槛。

## 3. 检测只观察与质量基线

对选定轮次生成当前答案集对应的 P3 相似性和 P4 异常报告。查看复核工作列表、P3/P4 的状态、规则/模型版本和证据。报告不参与评分计算；此阶段收集并审阅线索，不发布成绩。

使用去标识的样本按获批协议双人独立标注，并对分数与 `similarity_requires_review`、`anomaly_requires_review` 分歧逐例仲裁。用 [subjective-scoring 的双人标注评估工具](../../subjective-scoring/docs/calibration-evaluation.md) 先计算描述性基线；再审批严重误差定义及发布阈值。未覆盖的题型或模型版本应单独标记，不可外推质量结论。

保留原始标注、仲裁说明、真实模型输出、命令参数和 JSON 报告。若基线不满足已批准标准或出现未解释的严重误差，停留在只观察阶段，修复或重新校准后再评审。

## 4. 启用发布与逐步扩大

检测规则升级时先停止旧版检测进程，再部署候选版本并重新生成当前报告，确保任务记录的规则版本与实际处理程序一致。`score-consistency-v2` 要求重新生成旧版本 P4 报告后才能发布当前输入。

发布负责人确认 P2 发布/隔离执行、P6 指标、权限名单和演练记录通过后，才为指定发布人员创建或启用 `publisher` 账号。按受控轮次逐步扩大范围，每批完成后先检查：

- `/api/health` 正常，Compose 中 `postgres`、`exam`、`worker` 健康；worker `--health` 是数据库探活，发布前仍要通过 `--preflight` 检查评分链路。
- 评分队列无持续失败或过期租约，人工复核队列有负责人处理；P3/P4 报告与当前关闭轮次、答案集及评分代次一致。
- 阻断级 P4 线索均有复核处置，必需人工复核完成；发布 API 不返回 `REPORTS_NOT_READY`、`BLOCKING_FINDINGS_OPEN` 或复核未完成错误。
- P6 描述性指标相对基线没有触发团队已批准的停止条件。按轮次保存不可变发布批次、操作者、时间、版本与更正原因。

逐批记录样本范围、质量报告、未解决线索、发布版本、发布批次 ID 和继续/暂停决定。扩大前先由发布与复核负责人共同检查上一批，不按未经验证的固定百分比自动扩量。

## 5. 暂停与回滚

评分 worker 异常退出后，未超过 `max_attempts` 的任务在租约到期后可由其他实例领取；每次领取计一次尝试。最后一次租约仍有效时可继续完成，过期后下一次轮询会将任务标为 `dead`，当前评分代次的提交标为 `failed / need_review`，错误码为 `LEASE_ATTEMPTS_EXHAUSTED`。旧代次任务失败不会修改新代次成绩，失去租约的进程也不能修改已完成任务的错误信息。运维应核查进程退出、快照和 sandbox/provider 故障，再由有权限的人员发起新代次重评或人工处置；不要直接重置 attempts、租约或失败状态。

worker 完成、失败和耗尽清理采用答卷→任务锁顺序，与人工重评一致；清理跳过已锁定答卷。租约领取、续期和写回校验使用数据库实际时钟，长事务的起始时间不会延长旧租约的有效性。本地真实 Go API/worker 并发测试覆盖完成与最终失败交错、旧写回拒绝、当前新代次唯一入队，以及旧事务中完成/失败/续期均不能认可已过期租约。

每批试点记录队列深度、到期租约、dead/failed 数及最老等待时间，遇到持续增长时停止扩围。相似性批次入队对数据库序列化/死锁冲突最多执行三次完整事务，仍失败时请求明确失败，不能解释成“未发现异常”。本地合成验证已覆盖评分进程 SIGKILL 后恢复、旧租约拒写、尝试耗尽、旧代次失败隔离，以及 8 个并发 worker 处理 64 个任务无重复成绩历史；这些验证没有测量真实模型或生产部署的吞吐和延迟。

达到已批准的停止条件、健康检查失败、评分链路退化、报告持续过期或发现权限越界时，暂停新增轮次和发布；停止 worker 可避免新增评分任务。先保存日志、复核/队列状态、镜像摘要和数据库/`data/` 备份，保留已发布的成绩快照与审计记录。

若候选版本已通过“新 schema 上运行前一应用版本”的兼容演练，可按演练方案回退 Go 服务与 worker 镜像，同时保留数据库；不得假设旧二进制天然兼容新 schema。若必须恢复数据，应在维护窗口把数据库 dump 与同一时点的 `data/` 快照作为一组恢复到已验证版本。先核对备份时点之后新增的答卷、人工处置和成绩发布，制定保留或重放方案；不得直接覆盖并丢弃这些记录。恢复后再次检查 `/api/health`、容器健康、历史轮次和一条端到端评分，再决定是否开放服务。

不要手工删除迁移记录、修改已发布 migration 或直接编辑发布快照。缺少可验证的兼容路径或完整备份时，保持服务暂停并由数据库负责人制定恢复方案。

## 6. 历史成绩

`0012_review_audit` 为新人工复核记录绑定登录操作者、题目/子题及当前评分代次，为重评保存原因、前后代次与状态。人工复核必须明确填写分数和原因；重评请求使用 `{"reason":"具体原因"}`，缺少原因或队列未配置会明确失败。详情页在评分中、失败和完成态均可查看已有历史与审计。审计内容禁止 UPDATE；提交删除沿用既有级联策略，保留政策需要在发布流程中另外核准。

历史调分行的新字段为未知值，界面显示未记录；它们没有足够证据证明当时操作者/子题/代次，不可回填为当前账号或虚构重评事件。

迁移前已有的成绩仍作为历史记录保留，但没有新流程生成的版本化发布批次，因此不自动视为新流程审核通过，也不应伪造发布批次。若需按新流程重评，创建新的评分代次、完成必要复核与当前报告，再通过发布服务生成后继版本；原始历史成绩和后续更正链均保留。

题库审计与人工确认版本：`0013_question_bank_audit` 为创建、修改、导入、审核、启用、停用、归档记录实际登录操作者、原因、目标版本及前后内容，并在同一事务提交；写入失败不会留下已批准的版本。版本历史 API 返回 `audit_events`，前端展示只读记录。审计禁止 UPDATE/DELETE；不补造迁移前版本的操作者，直接旧调用缺少身份或原因时明确保留 NULL。

题库 HTTP 创建/修改请求须包含 `reason`，批量导入在外层对象包含 `reason`；审核、启停、归档请求须包含 `{"expected_version":2,"reason":"确认此版本题目及评分标准"}`。旧页面对已被编辑的版本执行审核会返回 409，需重新读取并审核当前内容。AI 提取仍产生候选，题库草稿不能直接启用或组卷，新编辑版本必须重新审核。旧无请求体的生命周期客户端需要同步升级。

P3/P4 检测队列租约：每次领取产生新的 `attempt_count`，完成、终止和重试写回同时匹配领取时的尝试次数、进程身份、running 状态及实际数据库时钟截止。数据库行锁等待之后重新验证截止，报告写入结束的状态更新也须在租约内；迟到的旧尝试返回 lease lost，不改写新报告。租约过期后由队列重新领取或标记尝试耗尽，失败/未完成状态仍不能当作“未发现异常”。

按条件抽题入口：试卷编辑器“从题库组卷”可按当前专业、知识点、难度、题型和关键词随机抽取 1–200 道当前已启用题目。抽题排除已选及当前试卷已有题库 ID；教师可取消勾选，再加入试卷并保存。`POST /api/admin/question-bank/sample` 接收 `count`、上述条件和 `exclude_ids`（最多1000项），仅题库编辑权限可调用。题量不足返回 409/INSUFFICIENT_QUESTIONS，不返回部分组卷结果；加入时通过 assembly-snapshot 重新检查当前版本，编辑/停用后的旧抽题预览会被拒绝。

逐题统计中，复合子题以 `父题ID/子题ID` 区分，避免不同复合题使用相同局部子题 ID 时混算；已完整限定的子题 ID 保持原样。空子题数组及旧记录的非数组子题字段按父题记录处理；缺少可识别父题的局部子题不生成猜测题目 ID。机器得分率与整卷审核完成后的最终得分率仍分开，partial_manual 不计入审核完成。`/api/admin/stats/breakdown` 的分组、逐题和发布分数在同一只读数据库快照读取；读报表期间提交的更正从下一次刷新可见。
